# OP-03 two-stage nightly backup — activation, verification and rollback runbook

22 Nov 2026 · PR #199 (Issue #124). **Draft. Nothing here has been run in production.**

## What changes

| | Legacy (deployed today) | Two-stage (this PR, OFF by default) |
|---|---|---|
| Trigger | `nightlyIntegrityJob` 02:00 | same 02:00 job = **Phase A**, plus one `finalizeNightlyIntegrityJob` 03:00 = **Phase B** |
| Phase A | capture + publish + verify + retention in ONE execution (timed out 17 Nov at 360.883 s) | capture under ScriptLock, publish per-sheet snapshots + `outpatient-pending-manifest-<day>`, set `INTEGRITY_PENDING_BACKUP`, stop |
| Phase B | — | re-read every published snapshot, typed SHA check, publish `outpatient-manifest-<day>` + `outpatient-verified-<day>` certificate, then retention, source inventory and sentinel; clear pending LAST |
| Restore | v2 manifest | v3 requires the certificate; v2 sets still readable |
| Switch | — | Script Property `INTEGRITY_TWO_STAGE_ENABLED=1`, set only by `setupIntegrityTwoStage()` |

Fail-closed: pending/active marker, missing finalizer trigger, tampered snapshot, missing manifest, retention failure → the job stops and keeps the prior certified set. No marker is auto-cleared.

## Gate 0 — native two-stage rehearsal (REQUIRED before production)

### One owner prerequisite — only ONE new standalone Apps Script project

An authorized owner creates a **NEW EMPTY STANDALONE** Apps Script project,
under restricted owner permissions, and supplies only its **Script ID**. It must
NOT be production Apps Script, a spreadsheet-bound project, a used QA project,
or a project with existing Script Properties. **Do not create three spreadsheets
manually, set source/backend secrets, Script Properties or triggers.** The new
`prepareTwoStageDrill()` creates three new private `OP03 TWO-STAGE SYNTHETIC ONLY`
spreadsheets itself; the runner refuses a reused project or any workbook outside
these three IDs. All source property accesses are transparently prefixed
`OP03_NATIVE_V3_`. The test's `MailApp` is a no-send facade. The exact
source and test file hashes are pinned to that isolated Script ID.

This is explicitly different from the obsolete Gate 0 instructions that asked
for **three pre-created sheets and manually configured properties**. Following
those old instructions makes the fresh-project guard fail and is unsafe.

### Push the actual A/B source to the isolated project — NOT a deployment

### Ordered native entrypoints — synthetic sheets only

Run each phase from the isolated Apps Script editor, recording its native
Execution ID, elapsed seconds, script/source SHA and status **privately**:

1. `prepareTwoStageDrill()` exactly once. This creates **three** distinct new
   Sheets files (synthetic source, backup and restore target) and seeds typed
   source families with 300 additional synthetic Clients, Leads, Payments and
   SessionLog rows, real preexisting fixture FinancialOps entries, plus
   synthetic `Sheet1` and `Copy of Clients`. Do not reset or delete them.
2. `expandTwoStageInventoryDrill()` repeatedly until the returned
   `scaleTabs` is **350/350**. It adds at most 20 very small synthetic tabs
   per invocation to the **synthetic backup**: 330 other-application tabs
   and 20 expired OUT tabs, to represent a ~381-tab destination without
   consuming the 10-million-cell quota. This is preparation, not the A/B timing.
3. `captureTwoStageDrill()` exactly once. It enables staged mode **only in
   namespaced synthetic Script Properties** then calls the real Phase A. Verify
   pending-only manifest and active/pending lifecycle, **no v3 certificate and
   no advanced row-loss baseline**. A's measured execution must be **under 300 s**
   for a practical margin to Google's 360 s hard limit.
4. `verifyTwoStageDrill()` once. It calls the real Phase B with the existing
   configured **synthetic** destination, performs full independent published
   data/readback + SHA/inventory validation, checks the v3 certificate, protects
   foreign/manual tabs, runs retention and clears pending only after certification.
   B must also complete **under 300 s**, independently of A. It repeats read-only
   verification from the actual published backup.
5. `restoreTwoStageDrill()` once. It copies every present typed and manual
   snapshot into the **third** isolated target, compares every grid against the
   verified manifest, and verifies that production-style operational cutover is
   correctly REFUSED when unclassified archive tabs lack their separately
   approved policy. This proves **physical full-data restore/readback** only,
   **not** operational reopening authorization.

The report is `_DrillReport` in the synthetic backup, with per-phase duration,
hashes, pass/fail, and explicit `productionCertified:false`. A failed,
timed-out or interrupted phase leaves the state fail-closed; **never silently
reset markers, reuse the old project, or re-run a phase to force green**.
Source/target workbook identifiers remain private. Separate disposable isolated
projects can test deliberate tampering, lost finalizer, duplicate admission,
retention failures and missing required source; those must all fail closed.

### Unclosed acceptance points that this harness cannot fake

- **Performance**: 300 synthetic rows per core family and a scaled ~381-tab
  destination approximate load but are not identical to live cell counts,
  network latency or current data size. One fast run is evidence, not a blanket
  production guarantee. Capture exact durations, per-phase headroom, and
  production-scale differences before approval.
- **Manual archives**: `Copy of Clients` and `Sheet1` are preserved and
  independently read back; a full operational restore remains **NO-GO** until
  the separate reviewed/pinned manual recovery policy is accepted, then exercised
  in another isolated test. Never drop or auto-whitelist those tabs.
- **Combined OUT #195 group journal**: this PR #199 branch is based on deployed
  source and does **not** by itself carry the unmerged group-credit journal
  `SessionOutcomeOps`. Run a source-hash-pinned isolated A/B and restore again
  against the **combined #195 candidate** when the harness is present there,
  verifying a NONEMPTY committed group intent and refusal of pending intents.
  Do not claim this PR's native run proves group settlement recovery.
- **Production**: a new 23 Nov OUT manifest was observed structurally in
  `EZONE-Backups`; it is not a proven 25/25 checksum verification, linked
  configured destination, nor an independent restore. Production inspection,
  freeze/drain, credential checks and subsequent deployment still need separate
  explicit authorization after the above acceptance gates.

## Production activation (after Gate 0 + Sandra's explicit approval)

1. Merge the PR; wait for Railway (`/api/version` = merge SHA); dispatch `deploy-apps-script.yml` with `expected_commit` = merge SHA. **Nothing changes yet — legacy mode continues.**
2. Confirm in the production script: exactly one `nightlyIntegrityJob` trigger, no `INTEGRITY_ACTIVE_BACKUP` / `INTEGRITY_PENDING_BACKUP` property, no recovery hold.
3. Run `setupIntegrityTwoStage()` ONCE from the editor. It refuses otherwise, creates one 03:00 finalizer, and sets the flag last.
4. Next morning: `outpatient-pending-manifest-<day>` after 02:00, `outpatient-manifest-<day>` + `outpatient-verified-<day>` after 03:00, both executions well under 360 s, no alert e-mail. Only then is the backup "verified".

## Rollback

- **Before `setupIntegrityTwoStage()`**: nothing to roll back; code is dormant.
- **After activation, no pending set**: delete the `finalizeNightlyIntegrityJob` trigger, delete `INTEGRITY_TWO_STAGE_ENABLED`. Legacy job resumes next night. Certified v3 sets stay readable.
- **After activation, pending set exists** (Phase B failed): do NOT clear `INTEGRITY_PENDING_BACKUP` blindly. First re-run `finalizeNightlyIntegrityJob` once; if it fails again, inspect the failure, keep the last certified set as the recovery point, then clear the marker only with the owner's explicit decision and record it on #124.
- **Code rollback**: redeploy the previous Apps Script version on the existing deployment (never a new deployment). Any v3 set already certified remains valid for v2-style inspection.

## Sheets invariants

Headers append-only; snapshot families only ever added (`pending-manifest`, `verified` are new names matched by `INTEGRITY_DATA_SNAPSHOT_RE`). Manual tabs (`Sheet1`, `Copy of Clients`) are captured as `other-<hash>` and never deleted by retention.
